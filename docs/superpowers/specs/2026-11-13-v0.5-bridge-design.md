# Aether Nexus v0.5 — the Bridge

**Status:** draft for approval, 2026-11-13
**Parent:** `docs/2026-10-10-aether-nexus-design.md` (§6.6, §11.4, §14). **Builds on:** `docs/superpowers/specs/2026-10-13-v0-skeleton-design.md`.

Items marked **(call)** were decided by the author of this document, not by the project owner; the owner reviews them here.

---

## 1. Intent

v0 is a CLI: every command opens the database, does one thing, and exits, and `launch`/`inspect` block the terminal until the agent returns. v0.5 adds a long-running server per galaxy and a browser page, the Bridge, so that the owner does **everything in the browser and goes to the terminal only for troubleshooting**.

"Everything" means everything the CLI can do today: the whole moon lifecycle at the `manual` rung, a live view of what is running, and the decision queue.

## 2. Goals, non-goals, anti-goals

**Goals**

1. `nexus serve` runs a server for the current galaxy and serves the Bridge page.
2. Every lifecycle action is available in the browser: create a system, assign a stream to a planet, assign a spec to a moon, launch, inspect, dock, reply, drop, park a stale voyage, cancel a running voyage, retire a ship.
3. The page updates live from the event log, including each running agent's activity.
4. Pending decisions are listed with their reasoning and their actions.
5. Several voyages can be in flight at once, bounded by config.
6. The provider order per role is editable from the browser.
7. Every existing CLI command keeps working unchanged, with or without the server running. Two CLI additions: `events --follow` (5.4) and `decision answer` (5.3).

**Done when:** with the fake adapter, a moon is assigned, launched, inspected to a REJECT, replied to, relaunched, inspected to an APPROVE and docked using only HTTP requests the page makes, while a second moon's voyage is in flight; and the owner has done the same once by hand in a real browser.

**Non-goals** (later phases)

- Any 3D scene. Fuel readings and the limiter. Rungs above `manual`: the rung is displayed, not changeable. `verdicts` is the first item of v1.
- Intake, and the `triage`/`decompose`/`plan` roles. Specs and stream missions are still hand-written.
- A spec editor in the browser. Specs are written in the owner's editor; the browser lists the files and assigns them.
- Carriers, planet → Fleet HQ merges, HQ → `main`.
- `doctor`, the Lanes v1 → v2 config migration command, the git allowlist, planet-level `plan` voyages (the `voyages` NOT NULL columns), reducers for `moon.settled`/`moon.emitted`/`moon.quarantined`.
- Remote access, multiple users, accounts.

**Anti-goals**

- The terminal must never depend on the server. If the server is down or broken, every CLI command still works.
- No control that edits something the server ignores. A setting appears in the Bridge only if changing it changes behaviour.
- No unattended behaviour. The server acts only on a human request.

## 3. Approaches considered

**How the CLI and the server share the work**

| Option | Trade-off |
|---|---|
| **A. Both write to the database directly (chosen)** | The CLI is untouched and never depends on the server. The server has to notice events it did not write, so it polls the log. Limits must be enforced in the database, not in server memory. |
| B. The CLI becomes a client of a running server | One writer. Every command needs a second code path, and the CLI fails in new ways exactly when the server is unhealthy. |
| C. Server required for everything | Simplest model; removes the troubleshooting fallback. |

**How the browser gets live updates**

| Option | Trade-off |
|---|---|
| **A. Server-sent events for the feed, HTTP POST for commands (chosen)** | The feed is one-way. The browser's built-in reconnect sends the last event id, which is the replay-from-cursor behaviour the parent design asks for. Node's built-in HTTP server is enough; no new runtime dependency. Departs from the parent design's "WebSocket" wording. |
| B. WebSocket | Needs the `ws` package plus hand-written reconnect and replay. Earns its cost only if the browser streams to the server, which nothing through v1.5 does. |

**What the page is built with**

| Option | Trade-off |
|---|---|
| **A. Preact + Vite (chosen)** | Components for lists that update live; named as an option in the parent design; the later Three.js scene can sit beside it. Adds a front-end build and dev dependencies. |
| B. Plain TypeScript | No tooling; hand-updating many live lists gets messy. |
| C. Svelte | Equally capable; Preact is smaller and stays in ordinary TypeScript. |

The owner chose A, A, A.

## 4. Constraints

- Node ≥ 22.13, `node:sqlite` (synchronous), TypeScript, tests with `node --test` on Linux, Windows and macOS in CI.
- The event log is the source of truth. Every state change is an appended event with a reducer; `db rebuild` must stay byte-equal.
- `Git` (`src/core/git.ts`) remains the only caller of git.
- The command functions in `src/server/commands/` remain the single implementation. The HTTP layer and the CLI are both thin wrappers over them.
- No new runtime dependencies. Preact and Vite are dev dependencies; the built page is static files.

## 5. Design

### 5.1 The server process

`nexus serve [--port <n>]` runs in the foreground in the galaxy's repo and prints the URL to open. It stops on Ctrl-C.

- **(call)** Default port 7341, overridable by `--port` or an optional `server.port` config key. If the port is taken, the command refuses with a clear message; it does not pick another.
- One server per galaxy. A `.nexus/server.json` file (pid, port, start time; git-ignored) records the running server. `serve` refuses if the file names a live process, and replaces it if the process is gone.
- On SIGINT/SIGTERM the server aborts every voyage it is running, which parks each as `interrupted` through the existing mechanism, then exits.

**Access control (call).** The server can launch agents and merge branches, so a web page open in another tab must not be able to drive it.

- It binds to 127.0.0.1 only.
- Each start generates a random token, printed as part of the URL. Opening that URL sets an HttpOnly, SameSite=Strict cookie and redirects to the bare URL. Every `/api` request requires the cookie.
- Requests whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` are rejected, as are POSTs whose `Origin` does not match.

### 5.2 Concurrency

- **Per-voyage git logging.** Today one mutable, galaxy-wide log hook is set and cleared by two callers: `runVoyage` (`src/server/dispatch.ts:125`, around the adapter call, during which no adapter currently calls `g.git`, so it logs nothing) and `dockMoon` (`src/server/commands/dock.ts:42`, which logs the dock's git commands on that moon's freighter voyage). With concurrency, a dock would log onto whichever voyage set the hook last, and whichever finished first would clear the other's hook. The mutable hook is replaced by a context carried with `AsyncLocalStorage`:
  - a dock still logs its git commands on its own freighter voyage, exactly as now;
  - git commands issued inside a voyage's adapter dispatch are logged on that voyage, as now;
  - nothing else is logged on any voyage. **(call)** The context is not widened to the server's own git work for a launch (worktree add, gate, snapshots, audit); the existing "launch yields exactly the adapter's events" assertion stays true.
- **Limits.** `scheduler.max_concurrent_ships` and `scheduler.per_provider_max` already exist in config and are unenforced. They are now checked inside the `voyage.launched` transaction by counting voyages in `launched`/`working`, so the limit holds across the server and any CLI process. Over the limit is a Refusal.
- **Provider choice respects the limits (call).** When no provider is named, `pickProvider` skips a provider that is at its `per_provider_max` as well as one with no idle ship, and takes the next in the role's order. A provider named explicitly is never substituted; it refuses.
- **Same moon twice.** Two launch requests for one moon must produce one voyage and one Refusal.
- **Owner.** `voyage.launched` records the launching process's pid. The server knows which in-flight voyages are its own.
- **Stale voyages (call).** A voyage in `launched`/`working` whose owner pid is not running is shown as stale, with the existing park-stale action. The server never parks it automatically; that stays a human action, as in v0.
- **Cancel.** A voyage the server owns can be cancelled from the browser. It parks as `interrupted`, the same path as Ctrl-C in the CLI.

Command functions other than `launchMoon` and `inspectMoon` are synchronous and briefly block the server's event loop (git calls are fast). That is accepted.

### 5.3 The main-tree check

**Today:** `runVoyage` snapshots the owner's working tree (HEAD plus the list of changed paths) before and after a voyage and parks the voyage as `main_tree_modified` on any difference. It cannot tell who made the change.

**Problem:** with a server running several long voyages, ordinary actions trip it: a commit, a new spec file, a reply to another moon (which writes the amended spec), a routing edit (which writes `.nexus/config.json`).

**Decided by the owner:**

1. **The system's own writes are exempt.** Any command that writes into the main tree first appends an event naming the paths (`replyMoon`: the spec; the routing edit: `.nexus/config.json`). When a voyage ends, paths named by such events appended since that voyage launched are removed from the comparison. This works across processes because it lives in the event log. The event kind needs a reducer, which may do nothing.
2. **Any other difference asks instead of parking.** The voyage proceeds exactly as if the tree were unchanged (returned, audited, holding). A decision of kind `main_tree_changed` is opened on the moon, carrying the same details the park carries today (HEAD before/after, paths appeared, paths vanished).
3. **Docking is refused while that decision is pending.**
4. **Two answers.** "That was me" resolves the decision and nothing else changes. "Not me" resolves it and parks the moon as `main_tree_modified`.

**Calls that make this fit the existing state machine:**

- **Everything that advances the moon waits for the answer.** While the decision is pending, launch, inspect, dock and reply are all refused with a message that says to answer it first. The owner was told "dock is refused"; this is stricter, so that the answer always lands on a moon that has not moved since the voyage ended. Drop is allowed and resolves the decision with outcome `drop`. *(As built, 2026-11-14: drop is offered and allowed only once the moon is parked — `adrift` or `quarantined`. On a moon that is not parked, for example `audited`, the owner answers the question first; "Not me" parks the moon, after which drop works. One extra click, no dead end.)*
- **`resolveDecisions` must not sweep it up.** Reply is refused (above), so the only command that closes this decision besides the answer is drop.
- **What "Not me" parks.** The voyage that saw the change may be an implement or a review voyage, so the moon can be in several states when the answer arrives:
  - the moon is already `adrift` or `quarantined` (the voyage parked for another reason, or the review returned REJECT): resolve only; it is already held for the human, and the decision's details stay in the log;
  - otherwise, if the moon's latest freighter voyage can legally go adrift (`holding`, `cleared`), run the standard park sequence on it with reason `main_tree_modified`;
  - otherwise (the freighter is `superseded` after a FIX verdict), park the moon directly with `moon.adrift`, as the carry-over park in `launch.ts` already does.
  The park opens the usual `adrift` decision, so reply and drop then work as for any park.
- **The CLI can answer it.** Voyages launched from the CLI open this decision too, and the terminal must not depend on the server. New command: `nexus decision answer <decision-id> --mine | --not-mine`. Pending decisions already appear in `nexus status`. The existing test that expects an immediate `main_tree_modified` park (`tests/server/launch.test.mjs`, I4a) changes to expect the decision.
- **One decision per voyage.** One human change during several voyages opens one decision on each moon; each is answered separately.

**Known gap, unchanged:** the snapshot compares which paths are changed, not their contents, so a change to a file that was already modified goes unseen. Not fixed in v0.5.

### 5.4 HTTP interface

All under `/api`, JSON, cookie required.

**Reads**

- `GET /api/snapshot` returns everything the page needs to draw from cold, plus `cursor`, the id of the last event it reflects:
  - systems, each with its planets and moons (barren bodies included);
  - voyages of current assignments, each marked own / other process / stale;
  - the fleet; pending decisions;
  - spec files under `pipeline.tasks_dir` not yet assigned, each with its task id and Touch list or the reason it does not parse;
  - `roles`, `scheduler` limits, the count in flight, `automation.level`.
- `GET /api/moons/<task-id>` returns one moon's detail: spec text, voyages, audits, verdicts, and its events (the activity log).
- `GET /api/events` is the live feed (server-sent events). One message per event row, with the event id as the message id. It starts after `Last-Event-ID` if the browser sends one, else after `?since=<id>`. The server polls the event table for new rows on one shared timer **(call: every 250 ms)** and sends a comment line as a heartbeat when idle.

**Commands:** `POST /api/commands/<name>` with a JSON body, one per command function, plus `config.roles` (5.5), `decision.answer` (5.3) and `voyage.cancel` (5.2).

| Result | Response |
|---|---|
| Done | 200 with the function's result |
| Refusal (`Refusal`, `TransitionRefused`, `GitRefusal`) | 409 with the message and any details |
| Bad input | 400 |
| Anything else | 500, and logged |

**Launch and inspect** do not hold the request open for the whole voyage. The request is answered as soon as the voyage is launched (202 with the voyage id) or as soon as the function refuses or returns without launching. `runVoyage` gains a callback for "launched" so the handler knows which happened. The rest of the function (audit, park, verdict) continues in the server.

**Failures after the response.** If that continuing work throws, the error must not be silent: it is logged, and shown in the browser against the moon. How it is carried to the browser is left to the builder.

**CLI.** `nexus events --follow` is implemented with the same polling and replaces the current "arrives with the daemon" refusal.

### 5.5 Routing order

The Bridge shows `roles.implement` and `roles.review` as ordered lists of configured providers and lets the owner reorder them. The server validates the whole candidate config with the existing validator, records the write (5.3), writes the file atomically, and reloads its config. The server already picks the first listed provider with an idle ship, so the order has a real effect. Adding or removing providers is not offered.

### 5.6 The page

One page, no routing library needed. **(call)** Layout:

```
┌ Aether Nexus · <repo> · rung: manual · in flight 2/6 ─────────── ● live ┐
│ DECISIONS (2)             │ SYSTEM S-20261113-demo ▾      [new system]  │
│ ▸ reject        T3   2m   │ Planet Kepler · stream P1                   │
│ ▸ tree changed  T5   now  │   Io        T1  merged                      │
│                           │   Europa    T3  quarantined          [open] │
│ FLEET                     │   Ganymede  T5  implementing         [open] │
│ codex   2 freighters idle │   Callisto  (barren)        [assign spec ▾] │
│ claude  1 customs working │ Planet Vega · (barren)      [assign stream] │
│                           ├─────────────────────────────────────────────┤
│ ROUTING                   │ MOON T3 · Europa      spec│activity│audit│verdicts
│ implement  codex ▲▼       │ REJECT round 1: "<reviewer reasoning>"      │
│            claude ▲▼      │ [ note ......................... ]          │
│ review     claude ▲▼      │ [Reply]  [Drop]                             │
└───────────────────────────┴─────────────────────────────────────────────┘
```

- **Header:** repo, rung (read-only), in-flight count against the limit, and a connection indicator that shows when the feed has dropped.
- **Decisions:** pending decisions, oldest first; selecting one opens its moon.
- **System view:** the selected system's planets and moons with status. Barren planets offer "assign stream"; barren moons of an assigned planet offer "assign spec" from the unassigned spec files.
- **Moon detail:** the spec, a live activity log of the moon's voyages, audits, verdict history, and only the actions valid for the moon's current state. After Reply, Launch is a separate click (manual rung).
- **A Refusal** is shown next to the control that caused it, with the server's message.

**Keeping the page current (call).** The server is the only place state is computed. The page holds the last snapshot; when feed events arrive it re-fetches the snapshot (debounced) and appends `voyage.event` rows straight to the open activity log. The page has no reducers of its own. The v1.5 scene, which needs to be a pure function of the event stream for replay, can change this then.

### 5.7 Layout in the repo and build

- **(call)** Server HTTP code under `src/server/http/`; the page under `web/` with its own tsconfig; built to `dist/web/` and served as static files by the server.
- `npm run build` builds both. `npm test` still builds first.

## 6. Testing

- **Server:** `node --test` suites against a real server on an ephemeral port with the fake adapter: access control (no cookie, wrong Host, wrong Origin), every command's success and refusal mapping, the feed (replay from a cursor, resume after reconnect, events written by another process appear), launch answering at "launched", cancel.
- **Concurrency:** while one voyage is in flight, another moon is docked: the dock's git events land on its own freighter voyage, none on the in-flight voyage, and the in-flight voyage finishes normally. Limits refused across two processes; provider skipped at its cap; double launch of one moon.
- **Main-tree check:** own writes exempt; a foreign change opens the decision; launch, inspect, dock and reply are refused while it is pending; "that was me"; "not me" from each of the moon states listed in 5.3; the CLI answer command.
- **End to end:** the "done when" script in §2, over HTTP, in CI on all three OSes.
- **Page (call):** no browser automation in CI for v0.5. The page stays thin (no state logic of its own), and the owner's manual walkthrough is part of "done". Revisit when the page gains logic.

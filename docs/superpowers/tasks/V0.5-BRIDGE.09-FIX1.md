## Objective
Three wrong behaviours and three test gaps remain in the commands route:
1. `POST /api/commands/<name>` answers 500 (with a TypeError on stderr) instead of 404 when `<name>` is an inherited `Object.prototype` member (`constructor`, `toString`, `__proto__`, `hasOwnProperty`, `valueOf`).
2. `runner.abortAll()` ignores a run that has started but not yet called `onLaunched`: it resolves at once, the run launches afterwards, is never aborted, and keeps flying after shutdown.
3. A run that rejects after launch with a value that cannot be converted to a string (e.g. `Object.create(null)`) throws inside the runner's settle handler: an unhandled rejection that kills the process.
4. Acceptance criteria 2 and 8 of the parent spec have no adequate test, and criterion 12's ship assertion can never fail.

## Context
This is fix round 1 for task V0.5-BRIDGE.09. Round 1 was reviewed: scope, interfaces, `src/server/http/server.ts` and every other criterion passed and must not change. The parent spec (`docs/superpowers/tasks/V0.5-BRIDGE.09.md`) still governs everything this delta does not mention. The command table is a plain object, so `COMMANDS["constructor"]` finds `Object`; that is the cause of item 1. Item 2 is not reachable over HTTP today (the command functions call `onLaunched` before their first `await`), but the runner is the only thing that owns voyages at shutdown and must not depend on that. Ship rows have the columns `id, name, class, fleet, status, voyage_count, last_event_id` — there is no `assignment_id`, which is why the current assertion `ship.status === "idle" || ship.assignment_id !== null` is always true. Affected workflow IDs is `none` because this project has no review suite.

## Interfaces
All exported signatures stay exactly as they are. Behaviour changes only:

```ts
// src/server/http/commands.ts
export function runCommand(g: Galaxy, runner: VoyageRunner, name: string, body: unknown): Promise<CommandOutcome>;
// D1: rejects with UnknownCommand for every name that is not an OWN key of the command table —
//     including "constructor", "toString", "__proto__", "hasOwnProperty", "valueOf" — before the body is validated.
//     Over HTTP these answer 404 { error } and write nothing to stderr.
//     Use an own-property lookup (Object.hasOwn) or a null-prototype table. No name blocklist.

// src/server/http/runner.ts — createVoyageRunner
// D2 (replaces the parent spec's abortAll line):
//   - The runner knows every run from the moment start() is called until that run settles, launched or not.
//   - abortAll(): marks the runner as shutting down, aborts the signal of EVERY such run (launched or not),
//     resolves only when all of them have settled, never rejects.
//   - A run that launches after abortAll() was called still resolves its start() promise
//     { launched: true, voyageId } and is tracked until it settles (its signal is already aborted,
//     so the command function parks the voyage as "interrupted").
//   - Unchanged: inFlight() counts launched, unsettled runs only; cancel(voyageId) finds launched runs only
//     and otherwise throws the same Refusal; start() after abortAll() rejects Refusal("the server is shutting down");
//     a run that fulfils or rejects without launching resolves/rejects start() as before.
// D3: the settle handling is total. Whatever value run rejects with after a launch, exactly one Failure
//     { ts, taskId, voyageId, message: <string> } is recorded (a fixed fallback such as "unknown error" when the
//     value cannot be converted to a string), one stderr line is written, onFailure is called once, the run is
//     untracked, and no unhandled rejection or uncaught exception occurs.
```

**Behavioral criteria** (each must be covered by a test in `tests/http/commands.test.mjs`, with exactly these titles):
- **T1 — "unknown command names inherited from Object.prototype answer 404"**: over HTTP, `POST /api/commands/<name>` for `constructor`, `toString`, `__proto__`, `hasOwnProperty`, `valueOf`, each with body `{}` and with `{"taskId":"T1"}`, answers 404; `events.maxId` is unchanged; `GET /api/ping` answers 200 afterwards.
- **T2 — "moon.launch on an audited moon answers 409 with the refusal and leaves nothing in flight"**: world `happy`; `moon.launch` over HTTP answers 202; wait (bounded) until moon T1's status is `audited`; a second `moon.launch` answers 409 with `error` matching `/is 'audited'/`; `x.w.g.db.all("voyages.inFlight")` is empty.
- **T3 — "each synchronous command maps success to 200 and a refusal to 409"**: one array of rows driven by one loop (rows may build their bodies lazily from earlier state). For each of the eight commands, a success answers 200 with `json.result` equal to the function's return value (deep-equal where it is deterministic, shape and types otherwise), and a refusal answers 409 with a string `error`. This sequence was verified by the reviewer in one `startWorld("slow")` world, in this order:
  - `system.create` `{slug:"two",title,brief}` → `{systemId: /^S-\d{8}-two$/, baseSha, planets, moons}`; the same body again → 409.
  - `planet.assign` `{systemId: x.w.systemId, streamId:"P2", mission:"m", territory:["src/**"]}` → `{planetId, branch, worktree, discovered}`; `systemId:"nope"` → 409.
  - `moon.assign` with `specPath` from `writeSpec(x.w.dir, "T2")` (import `writeSpec` from `tests/helpers.mjs`) → `{moonId, taskId:"T2", discovered:false, attention:{}}`; the same body again → 409.
  - `moon.launch` T1 (202), then `moon.park` `{taskId:"T1", reason:"gone"}` → `{voyageId: <the launched id>, reason:"stale:gone"}`; again → 409.
  - `moon.reply` `{taskId:"T1", note:"carry on"}` → `{round:2}`; `{taskId:"T2", note:"x"}` → 409.
  - `moon.drop` `{taskId:"T1"}` → `{moonId: x.w.moonId}`; again → 409.
  - `fleet.retire` on an idle ship id from `ships.all` → `{retired:true}`; again → 409.
  - `config.roles` `{role:"review", order:["fake"]}` → `{roles:{implement:["fake"],review:["fake"]}}`; `order:["nope"]` → 409.
- **T4 — "abortAll aborts and awaits a start that has not launched yet"**: `createVoyageRunner` directly: a `run` that waits before calling `onLaunched`; `abortAll()` called before the launch aborts that run's signal and resolves only after the run has settled; the `start` promise still resolves `{ launched: true, voyageId }`; `inFlight()` is 0 afterwards; a later `start` rejects with the shutting-down refusal. In the same test or a neighbouring one: a run that rejects after launch with `Object.create(null)` records one `Failure` with a string `message`, calls `onFailure` once, and `inFlight()` returns to 0.
- **T5 — "closing a server parks its voyage, leaves every ship consistent, and projections rebuild exactly"** (replaces the test "closing a server aborts and parks its voyage and projections rebuild exactly"): `slow` voyage launched over HTTP (202); then immediately after `await x.srv.close()`, with no further waiting: the voyage row is `adrift`; the moon's `park_reason` is `interrupted`; `voyages.inFlight` is empty; the ship whose id is the voyage row's `ship_id` has status `adrift`; every other ship is `idle`; `rebuild` leaves `dumpProjections` byte-equal. The test ends with `finally { await x.close(); }` (safe after `srv.close()`, which is memoized, and it removes the temporary webRoot). The expressions `ship.assignment_id !== null` and `x.w.cleanup()` no longer appear in the file.

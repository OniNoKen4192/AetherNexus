## Objective
The server answers `GET /api/snapshot` with the whole state a browser page needs to draw the galaxy, and `GET /api/moons/<task-id>` with one moon's detail including the list of actions that are valid for it right now.

## Context
Aether Nexus has a local HTTP server (`nexus serve`) that a browser page will use. The page holds no state rules of its own: it draws what the snapshot says and shows exactly the action buttons the server lists, so `availableActions` must agree with what the command functions actually accept. Voyages can be started by this server process, by another process (the CLI), or by a process that has since died; the page must tell these apart, which is why each in-flight voyage gets an `owner`. Both routes are reads: they must never append an event or write a file. Access control is already enforced before any `/api/*` handler runs; do not add or change checks. Affected workflow IDs is `none` because this project has no review suite.

## Constraints
- `snapshot`:
  - `cursor` is read FIRST (`events.maxId`), before any other query, so a client that follows the event feed from `cursor` cannot miss a change.
  - `repo` is the base name of `g.repoRoot`; `rung` is `g.config.automation.level`; `limits.in_flight` is the number of `voyages.inFlight` rows.
  - `systems` is every system in `showSystem`'s shape flattened as `{ ...system, planets }`, barren planets and moons included.
  - `voyages` is the voyages of every currently assigned moon (by its `assignment_id`), plus `owner`.
  - `owner` is `null` unless the voyage status is `launched` or `working`. Otherwise it comes from the `owner_pid` field of that voyage's `voyage.launched` event payload: equal to `ctx.ownPid` → `"server"`; else `pidAlive(owner_pid)` → `"other"`; dead or absent → `"stale"`.
  - `specs` is every `*.md` file directly under `g.paths.specs` whose task id is not currently assigned to a moon, as `{ path (repo-relative, forward slashes), taskId, touch, error }`. A file that cannot be read or parsed, has no Task ID, or has an empty Touch list is still listed, with `error` set to a one-line reason and `taskId` `null` when unknown. A missing specs directory gives `[]`. Nothing here may throw.
  - `failures` is `ctx.failures` as given.
- `moonDetail`: `spec` is the text of the moon's `spec_path` file, or `null` if it is missing; `voyages`, `verdicts` and `events` are those of the moon's CURRENT `assignment_id` only; `decisions` is `decisions.pendingByTarget` for the task; `actions` is `availableActions`.
- `availableActions`, first matching row wins:

| State of the moon | Actions, in this order |
|---|---|
| a pending `main_tree_changed` decision exists | `answer`, then `drop` if the moon is `adrift` or `quarantined` |
| `emitted` or `gated` | `launch` |
| `implementing` or `reviewing` with a voyage `launched`/`working` | `cancel` if its owner is `server`; `park_stale` if `stale`; none if `other` |
| `audited` | `launch` if the latest verdict of the assignment is `FIX`, else `inspect` |
| `reviewing`, latest verdict `APPROVE`, latest implement voyage `cleared` or `en_route` | `dock` |
| `adrift` or `quarantined` | `reply`, `drop`, then `launch` if `repliedSincePark` is true |
| anything else (`merged`, `dropped`, …) | none |

- Reads only: no `append`, no file writes, no git commands.
- No new SQL and no new dependencies. Node ≥ 22.13, ES modules, TypeScript strict.
- Tests use `node:test` and `node:assert/strict`, import compiled code from `dist/`, and call `close()` / `cleanup()` in `finally`.

**Behavioral criteria** (each must be covered by a test in `tests/http/reads.test.mjs`):
1. `GET /api/snapshot` on a fresh world: `cursor` equals the maximum event id; `systems[0].planets` includes barren planets and each planet's barren moons; `rung` is `"manual"`; `limits.in_flight` is 0; `roles` matches the config.
2. A spec file written to the specs directory but not assigned appears in `specs` with its task id and Touch list; the spec already assigned to `T1` does not.
3. A spec file with unparseable content and one with no Touch list are each listed with a non-null `error`, and the route still answers 200.
4. A voyage whose `voyage.launched` event carries `owner_pid: 2147483646` (a dead pid; build the state by appending the same events the launch code appends, with that pid) is `owner: "stale"`, the moon's `actions` are `["park_stale"]`, and `limits.in_flight` is 1; after `parkStaleMoon` it is 0 and the voyage's `owner` is `null`.
5. Walking one moon through `launch → inspect (APPROVE) → dock` with the fake adapter, at every stage each action listed by `availableActions` is accepted by its command function, and `launchMoon`, `inspectMoon` and `dockMoon` are refused whenever their action is not listed. The stage lists are exactly `["launch"]`, `["inspect"]`, `["dock"]`, `[]`.
6. After a REJECT the actions are `["reply","drop"]`; after `replyMoon` they are `["reply","drop","launch"]`. After a FIX verdict they are `["launch"]`.
7. With a pending `main_tree_changed` decision on an `audited` moon the actions are exactly `["answer"]`.
8. `GET /api/moons/T1` returns the spec text, and only the voyages, verdicts and events of the current assignment: after `dropMoon` and re-assigning the same spec, the earlier assignment's voyages and events are absent.
9. `GET /api/moons/nope` is 404 with an `error` message; `GET /api/moons/` and `GET /api/moons/a/b` are 404.
10. Neither route appends an event: the maximum event id is the same before and after calling both.

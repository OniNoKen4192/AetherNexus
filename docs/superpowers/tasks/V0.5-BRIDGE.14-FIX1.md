## Objective
A control group in the moon action bar keeps its state (request in flight, error message, field text, chosen provider, open drop confirmation) when the server's action list changes around it for the same moon. Today the group is thrown away whenever its action moves to another position in `detail.actions`.

Observable wrong behaviour now: a parked moon that was replied to shows `reply`, `drop`, `launch`. Launch is clicked while the ship limit is reached; the server gates the moon and refuses with `1 voyage in flight — the limit is 1 (scheduler.max_concurrent_ships)`; the moon's actions become `launch` alone. The refusal appears and then vanishes when the detail reloads, and the chosen provider resets. If the reload arrives before the answer, Launch is enabled again while the request is still in flight and the refusal is never shown.

## Context
The control rule of V0.5-BRIDGE.14 says a failed result's message stays in its group until that group's next send starts, and that a group is disabled while its request is in flight. `ActionBar` keys each group with the task id, the action name and the entry's index in `detail.actions`. The index makes the key change when other actions leave or join the list, so Preact remounts the group. The task id in the key is correct and must stay: it is what resets local state when another moon is opened. The server's list never repeats an action (every path of `availableActions` in `src/server/commands/query.ts` returns distinct names), so the task id and the action name already form a unique key. Everything else in round 0 passed review; change nothing else. Affected workflow IDs is `none` because this project has no review suite.

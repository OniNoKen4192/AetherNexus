## Objective
Three wrong behaviours in the round-0 components are corrected:
1. A moon with no task id is never a clickable or selected row.
2. A failed refresh shows its error above the loaded moon detail instead of replacing it.
3. An activity log that has just appeared follows the bottom.

## Context
Round 0 passed every machine check; these defects were found by reading the code. Everything not named here is correct and must stay as it is. The store keeps `b.detail` when a refresh fails and only sets `detailError`, so an error and a detail can be present together. Components cannot be rendered under `node --test`, so the machine check is a few fixed facts about the source text; a reviewer reads the behaviour. Affected workflow IDs is `none` because this project has no review suite.

## Constraints
- **Item 1, `SystemView.tsx`**:
  - A moon is a `.row` only when its `task_id` is a string. Only such a row has a click handler, which calls `b.openMoon(taskId)` with no guard, and only such a row can carry `selected`.
  - Any other moon renders as the existing non-row line (`system-barren-moon`): its name, plus the word `barren` only when `body_status` is `barren`.
  - The text `taskId !== null && b.openMoon` must no longer appear in the file.
- **Item 2, `MoonDetail.tsx`**:
  - After the `b.taskId === null` guard there is one panel root. The text `panel moon-detail` appears exactly once in the file.
  - Inside it, in this order: the bar with the title and `Close`; the `.msg-error` when `detailError` is not null; `Loading` when `b.detail` is null and `detailError` is null; the heading, `park_reason` line, tabs and open tab when `b.detail` is not null.
  - An error with a loaded detail shows both. An error with no detail shows the error and no `Loading`.
- **Item 3, `MoonDetail.tsx`**:
  - Keep the `followBottom` ref and the existing reset on `b.taskId` change.
  - Add a second `followBottom.current = true` that takes effect when the activity log element appears (for instance when the Activity tab is opened), so a newly mounted log is scrolled to the bottom.
  - The reset must be in place before that commit's scroll-to-bottom layout effect runs. A `useEffect` runs after it and is too late; use the tab's click handler, a ref callback, or a layout effect declared before the scrolling one.
  - While the log stays mounted, behaviour is unchanged: it follows unless the reader is more than 24 px above the bottom.
- Change nothing else: no new state, no new dependencies, no CSS, no change to the tabs, activity lines, audit or verdicts.
- TypeScript strict; `npm run build:web` prints no errors. Keys stay on every list.

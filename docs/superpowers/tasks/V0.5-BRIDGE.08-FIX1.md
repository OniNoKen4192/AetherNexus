## Objective
1. `feed.handle()` never returns when it is given a response that is already destroyed and at least 500 events lie after the client's cursor. It re-reads the same `events.page` forever in one synchronous loop, which freezes the whole server process. After this task it returns promptly.
2. Three behaviours have no test that can fail. Deleting the per-client id filter (`row.id <= client.lastId`) leaves all 12 feed tests green; so does deleting `client.res.end()` from `close()`. The criterion 4 test never kills its child process and waits for it without a bound. After this task each of these is pinned by a test.

## Context
`src/server/http/feed.ts` and `tests/http/feed.test.mjs` were created by V0.5-BRIDGE.08 and reviewed. The feed's delivery behaviour is correct and must not change: under a multi-process stress run every client received exactly cursor+1..max. This round fixes one loop-termination bug and strengthens tests; it is not a redesign. In the backlog loop of `handle`, `sendRows` returns early without advancing `client.lastId` when the response is destroyed, so a full page is fetched again with the same cursor. The page-length rule (stop on a page shorter than 500) is accepted and stays. Affected workflow IDs is `none` because this project has no review suite.

```bash
npm test -- "tests/http/*.test.mjs" && node --disable-warning=ExperimentalWarning --input-type=module -e 'import http from "node:http"; import { makeGalaxy } from "./tests/helpers.mjs"; import { append } from "./dist/db/events.js"; import { createFeed } from "./dist/server/http/feed.js"; const w = await makeGalaxy(); const g = w.g; for (let i = 0; i < 600; i++) append(g.db, { kind: "tree.written", payload: { paths: ["x"] } }); let pages = 0; const all = g.db.all; g.db.all = (n, p) => { if (n === "events.page" && ++pages > 50) throw new Error("backlog loop does not stop on a destroyed response"); return all(n, p); }; const feed = createFeed(g, { pollMs: 1000 }); let failed; const server = http.createServer((req, res) => { res.destroy(); try { feed.handle(req, res, new URLSearchParams("since=0")); } catch (e) { failed = e; } }); await new Promise((r) => server.listen(0, "127.0.0.1", r)); await new Promise((r) => http.get({ host: "127.0.0.1", port: server.address().port, path: "/", agent: false }, (res) => res.resume().on("close", r)).on("error", r)); feed.close(); server.closeAllConnections(); await new Promise((r) => server.close(r)); w.cleanup(); if (failed) { console.error("FAIL: " + failed.message); process.exit(1); } console.log("ok: handle returned after " + pages + " page queries");'
```

**Behavioral criteria** (each must be covered by a test in `tests/http/feed.test.mjs`):
1. Destroyed response: with at least 600 events after the cursor, a hand-made `http.createServer` handler destroys the response and then calls `feed.handle(req, res, query)` with `since=0`. The call returns, does not throw, and issues at most 2 `events.page` queries. A second, normal client connecting afterwards with `since=0` receives ids `1..N` complete and ascending.
2. Hand-over without duplicates (replaces the body of "clients with different cursors each retain a complete ordered stream"). Start the server with `pollMs` of at least 300, so the poller has not yet read what the client's backlog reads. Read cursor `c` (the current maximum id), append several events, then connect client A with `since=c`. Keep appending in at least 5 separate transactions with an event-loop turn between them; that appending starts before A connects and ends after a second client B (`since=0`) has connected and received its backlog. Append one last event and wait until both clients have received it. Assert A's ids are exactly `c+1..max` and B's are exactly `1..max`, each strictly ascending with no id repeated. This test must fail when the `row.id <= client.lastId` filter is removed from `sendRows`.
3. The criterion 4 test kills its child process in `finally` if it is still running, and its wait for the child is bounded (it rejects after a timeout such as 20 s instead of waiting forever).
4. `feed.close()` on its own (`createFeed` directly, hand-made server, two connected clients): after `feed.close()` both clients' `closed` resolve within a bounded wait, before `server.closeAllConnections()` or `server.close()` is called. Events appended after `close()` cause no further `events.page` query (count them through a wrapper on `g.db.all`, waiting on a condition bounded by time). A second `close()` and a `notify()` after it do not throw. This test must fail when `client.res.end()` is removed from `close()`.

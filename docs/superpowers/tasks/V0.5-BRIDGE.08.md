## Objective
`GET /api/events` streams the event log to a browser as server-sent events: a client receives every event after its cursor, in order, exactly once, first the backlog and then new events as they are appended by any process.

## Context
Aether Nexus has a local HTTP server (`nexus serve`) and a browser page that re-reads a snapshot whenever something happens. This task is the "something happened" channel. Server-sent events were chosen over WebSocket because the stream is one-way, needs no dependency, and the browser's `EventSource` reconnects by itself and sends `Last-Event-ID`, which gives resume for free. The event log is SQLite and is also written by other processes (the CLI), so the feed polls it through the existing `followEvents` poller; one poller serves every connected client. The correctness property that matters: a page that reads a snapshot (which carries a `cursor`) and then connects with that cursor must miss nothing and see nothing twice, however many events land in between. Access control already runs before any `/api/*` handler; do not add or change checks. Affected workflow IDs is `none` because this project has no review suite.

Wire format (exact bytes; `\n` is a single line feed):

```text
response headers:  Content-Type: text/event-stream; charset=utf-8
                   Cache-Control: no-store
one event row:     id: <id>\ndata: <JSON>\n\n
                   <JSON> is JSON.stringify of the EventRow (rowToEvent's result: payload is an object, not a string), on one line
server event:      event: server\ndata: {}\n\n          (no id line)
heartbeat:         : hb\n\n                             (a comment line; sent to a client that has received nothing for heartbeatMs)
```

Start cursor of a client, first match wins: the `Last-Event-ID` request header if it is a non-negative integer; else the `since` query parameter if it is a non-negative integer; else the current maximum event id (the client starts at the present). A header or parameter that is present but not a non-negative integer answers `400` with a JSON `{ error }` body instead of opening a stream.

## Constraints
- One `followEvents` poller per feed, started at the current maximum id when the feed is created and stopped only by `close()`. Not one poller per client.
- No gap and no duplicate, by construction: each client keeps the id of the last event written to it. When a client connects, its backlog is read from the database with `events.page` (pages of 500 until empty) starting at its cursor and written before it joins the live set; a live batch is written to a client only for rows whose id is greater than that client's last id. Everything from reading the backlog to joining the live set happens synchronously in one tick.
- A client is removed when its response closes or errors. A write to a destroyed response must not throw into the poller or affect other clients.
- The stream never ends from the server side except through `close()`. Call `res.flushHeaders()` (or write the first bytes) immediately so the client sees the response open even when there is no backlog.
- `notify()` writes the `server` event to every connected client immediately, not on the next poll.
- The heartbeat timer is `unref`'d and cleared by `close()`; a feed with no clients keeps nothing alive.
- `close()` leaves no timer and no open response behind: after `srv.close()` in a test the test process must be able to exit.
- Reads only: the feed never appends an event.
- No new SQL and no new dependencies (`node:http` only). Node ≥ 22.13, ES modules, TypeScript strict.
- Tests use `node:test` and `node:assert/strict`, import compiled code from `dist/`, wait on conditions with bounded timeouts, never fixed sleeps as the pass condition, and close feeds, servers and child processes in `finally`.

## Acceptance

**Test command (must exit 0):**
```bash
npm test -- "tests/http/*.test.mjs"
```

**Behavioral criteria** (each must be covered by a test in `tests/http/feed.test.mjs`):
1. With at least 1500 events in the log (append them inside one `g.db.transaction` to keep the test fast), a client connecting with `since=0` receives ids `1..N` strictly ascending with none missing or repeated; an event appended afterwards arrives exactly once.
2. `Last-Event-ID: <k>` resumes after `k`, and wins over a different `?since=`.
3. A client with no cursor receives none of the existing events, then receives an event appended after it connected.
4. An event appended by another process arrives: spawn `node dist/cli/main.js system create other --title t --brief-text b` with the galaxy as its working directory and expect a `system.created` event on the feed.
5. Activity arrives while a voyage is in flight: with the `slow` script, start `launchMoon` without awaiting it and observe a `voyage.launched` event for it on the feed before the launch promise resolves.
6. `notify()` produces exactly one `server` event on every connected client (drive it through a test-only route is NOT allowed; obtain the feed by calling `createFeed` directly on a galaxy with a hand-made `http.createServer`, or assert through whatever `startServer` exposes without adding public surface beyond the Interfaces above).
7. Two clients with different cursors connected at the same time each receive a complete, strictly ascending stream from their own cursor, while events are being appended.
8. A client that disconnects is dropped: after it closes, further appends and a `notify()` cause no error, and a second client still receives everything.
9. `?since=abc`, `?since=-1` and `Last-Event-ID: x` each answer 400 with an `error` field.
10. The response has `Content-Type` starting with `text/event-stream` and `Cache-Control: no-store`; `GET /api/events` without the cookie is 401.
11. With `heartbeatMs: 50` an idle client receives a `: hb` comment (test through `createFeed` directly).
12. `close()` ends every open stream (`closed` resolves) and `srv.close()` resolves.

## Objective
From the system view the owner can create a system, assign a stream to a barren planet, and assign a task spec to a barren moon, each through its HTTP command.

## Context
The Bridge is a Preact page (sources in `web/src`, built by Vite into `dist/web`) served by `nexus serve`. The page decides nothing and applies nothing locally: a form sends a command, the server accepts or refuses it with a message, and the event feed brings the new state. Task 13 built the system view; Task 14 built the `useCommand` hook that carries a control's busy and error state. Unassigned spec files the server found on disk arrive as `snapshot.specs`; an entry with an `error` cannot be assigned and says why. Components cannot be rendered under `node --test`, so the machine check is the type check, the build, and a test of the built bundle's copy; a person checks the behaviour in a browser later. Affected workflow IDs is `none` because this project has no review suite.

The HTTP commands and their JSON bodies (the server rejects unknown or missing fields; string fields must be non-empty; optional fields are omitted, never sent as `""` or `null`):

| Command | Body |
|---|---|
| `system.create` | `{ slug, title, brief, kind?: "feature" \| "bug" }` |

| `moon.assign` | `{ planetId, specPath, moonName }` |

`system.create` answers with data `{ systemId: string, … }`. To read it, a form may call `b.run` directly in place of `useCommand().send`, provided it still follows the control rule below.

## Constraints
- **NewSystem**: a `New system` button that reveals, inline, a form with `slug`, `title` and `brief` (textarea) fields, a `kind` select (`feature`, `bug`; `feature` first) and `Create` and `Cancel` buttons. `Create` is disabled while any of the trimmed slug, title or brief is empty. It sends `system.create` with the trimmed values and the chosen kind. When accepted, the form closes and clears, and `b.selectSystem(<the new systemId>)` is called. `SystemView` mounts it in every state where the snapshot is loaded, including when there are no systems.
- **AssignStream**: `SystemView` mounts one beside each planet whose `body_status` is `barren`, passing the shown system's id and the planet's name. It is an `Assign stream` button that reveals, inline, a form with `stream id` and `mission` fields, a `territory` textarea (one glob per line) and `Assign` and `Cancel` buttons. `Assign` is disabled while the trimmed stream id or mission is empty or the territory has no non-blank line. It sends `planet.assign` with `territory` as the array of trimmed non-blank lines. When accepted, the form closes.
- **AssignSpec**: `SystemView` mounts one beside each moon whose `body_status` is `barren` and whose planet's `body_status` is `assigned`, passing the planet's id and the moon's name. It is an `Assign spec` button that reveals, inline, a `<select>` over `snapshot.specs` and `Assign` and `Cancel` buttons. An entry without an error is an option labelled `<taskId> — <path>`; an entry with an error is a disabled option labelled `<path> — <error>`. The first option is a disabled placeholder `Choose a spec`. `Assign` is disabled until an assignable spec is chosen. It sends `moon.assign` with `specPath` set to the entry's `path`. With no entries in `snapshot.specs` the form shows exactly `No unassigned specs.` and no select. When accepted, the form closes.
- **The control rule** (each form has its own request state): every button and field of a form is disabled while its request is in flight; a failed result's message is shown in a `.msg-error` inside that form and stays until that form's next send starts or the form is cancelled; nothing is updated optimistically — the page does not alter `snapshot` itself.
- A barren moon or planet keeps showing `barren` as Task 13 made it; the forms are additions beside it.
- Local state is view state only (whether a form is open, field text, the chosen option, busy and error). No component calls `fetch`.
- No browser dialogs: no `confirm(`, `alert(` or `prompt(` anywhere in the Touch files.
- `web/src/style.css`: add rules only, below the existing ones; do not edit or remove an existing rule. Use the existing classes (`.btn`, `.field`, `.msg-error`) and colour variables; add no new colours, fonts or external resources.
- Keys on every list rendered from an array. Text is rendered as text (no `dangerouslySetInnerHTML`).
- No new dependencies. TypeScript strict; `npm run build:web` prints no errors.
- The test reads the built bundle from `dist/web/assets/*.js` read-only: it never passes `dist/web` to `startWorld` (that helper deletes its web root on close) and never writes under `dist/`. It fails with a clear message when `dist/web/assets` is missing.

## Objective
`POST /api/commands/<name>` runs the existing command functions for a browser: short commands answer with their result, launch and inspect answer as soon as the voyage has launched and keep running in the server, a running voyage can be cancelled, and stopping the server parks every voyage it owns.

## Context
Aether Nexus has a local HTTP server (`nexus serve`) whose page drives the whole moon lifecycle. All behaviour already lives in command functions under `src/server/commands/`; this task is a thin, strict adapter in front of them, plus a small runner that owns the voyages this server process started. A voyage takes minutes, so the HTTP request cannot wait for it: the page gets the voyage id back at once and follows progress on the event feed. If a voyage's continuing work fails after that answer, nobody is waiting on a promise, so the failure must be recorded where the page can see it. Two browser tabs may send the same command; the second must get a clean refusal, never a second effect. Access control already runs before any `/api/*` handler; do not add or change those checks. Affected workflow IDs is `none` because this project has no review suite.

## Interfaces

Produced:

```ts
// src/server/http/runner.ts
import type { Failure } from "../commands/query.js";
export type VoyageRunner = {
  start(
    taskId: string,
    run: (o: { signal: AbortSignal; onLaunched: (voyageId: string) => void }) => Promise<unknown>,
  ): Promise<{ launched: true; voyageId: string } | { launched: false; result: unknown }>;
  cancel(voyageId: string): void;
  abortAll(): Promise<void>;
  failures(): Failure[];
  inFlight(): number;
};
export function createVoyageRunner(opts: { onFailure: () => void }): VoyageRunner;

// src/server/http/commands.ts
export type CommandOutcome = { status: 200; body: { result: unknown } } | { status: 202; body: { voyageId: string } };
export function runCommand(g: Galaxy, runner: VoyageRunner, name: string, body: unknown): Promise<CommandOutcome>;
// Throws: UnknownCommand (→ 404), BadRequest (→ 400), or whatever the command function throws.
export class UnknownCommand extends Error {}
export class BadRequest extends Error {}
export function errorResponse(e: unknown): { status: number; body: { error: string; details?: unknown } };

// src/server/http/server.ts
export type ApiContext = { g: Galaxy; req: http.IncomingMessage; res: http.ServerResponse; query: URLSearchParams; feed: Feed; runner: VoyageRunner };
```

Runner semantics:
- `start` calls `run` once with a fresh `AbortSignal` and an `onLaunched` callback.
  - `onLaunched(voyageId)` fires first → the returned promise resolves `{ launched: true, voyageId }` at that moment, while `run` keeps going. The run is then tracked under that voyage id until it settles.
  - `run` fulfils without ever launching → resolves `{ launched: false, result }`.
  - `run` rejects without ever launching → the returned promise rejects with that error.
- After a launch, when `run` later rejects: record a `Failure` `{ ts: <ISO time>, taskId, voyageId, message: <error message> }`, write one line to stderr, call `opts.onFailure()` (a throwing `onFailure` is caught). When it fulfils: record nothing. Either way the run is no longer tracked.
- `cancel(voyageId)` aborts that run's signal. Not tracked → `Refusal("voyage <id> is not running in this server")`.
- `abortAll()` aborts every tracked run, resolves when all have settled, never rejects. After `abortAll()` has been called, `start` rejects with `Refusal("the server is shutting down")`.
- `failures()` returns the newest first, at most 50.
- `inFlight()` is the number of tracked runs.

```text
moon.reply        { taskId: string, note: string }                                                          replyMoon

```

Responses:

```text
200 { result: <the function's return value> }
202 { voyageId }                       moon.launch / voyage.inspect once launched
                                       (a run that finishes without launching answers 200 { result })
400 { error }                          body is not valid JSON, is not a plain object, a required field is missing,
                                       a field has the wrong type or an enum value outside its list, a string field is empty,
                                       a number field is not a finite integer, or the body has a field the command does not list
404 { error }                          unknown command name
409 { error, details? }                Refusal (details = its .details when set), TransitionRefused, GitRefusal
413 { error }                          body larger than 1 MiB (stop reading and answer; do not buffer the rest)
415 { error }                          Content-Type is not application/json
500 { error: "internal error" }        anything else; the real error goes to stderr, never to the client
```

## Constraints
- `src/server/http/server.ts` changes, and only these:
  1. One runner per server: `createVoyageRunner({ onFailure: () => feed.notify() })`, passed to handlers in `ApiContext`.
  2. A prefix route `"POST /api/commands/"` that enforces the content type, reads the body with the 1 MiB limit, calls `runCommand`, and maps errors with `errorResponse`.
  3. `GET /api/snapshot` passes `failures: runner.failures()`.
  4. `close()` order: `await runner.abortAll()`, then `feed.close()`, then close the HTTP server and release the lock.
  5. The catch in `http.createServer` answers `500 { error: "internal error" }` and writes the real error to stderr (today it echoes the error message, which can contain file paths).
  6. `query` is built with `new URLSearchParams(<the part of req.url after the first "?">)` so an odd path such as `//[x` can no longer throw (today it becomes a 500).
- Validation is table-driven: one declaration per command of its fields (type, optional or not, enum values), one generic validator. No per-command hand-written `if` chains.
- A handler passes the command function only the declared fields, never the raw body object.
- `moon.assign`: if `specPath`, resolved against the repository root, lies outside the repository root, answer 400 without reading anything. (Check whether `assignMoon` already refuses this; the 400 must hold either way.)
- `moon.launch` and `voyage.inspect` never pass `onEvent` or `reviewScript`.
- Nothing in this task calls a command function without a POST from a client. The server starts no voyage by itself.
- No new SQL and no new dependencies. Node ≥ 22.13, ES modules, TypeScript strict.
- Tests use `node:test` and `node:assert/strict`, import compiled code from `dist/`, wait on conditions with bounded timeouts, and call `close()` in `finally`. A test must not leave a voyage in flight when it ends.

## Acceptance

**Test command (must exit 0):**
```bash
npm test -- "tests/http/*.test.mjs"
```

**Behavioral criteria** (each must be covered by a test in `tests/http/commands.test.mjs`):
1. `moon.launch` with the `slow` script answers 202 with a voyage id while that voyage's row is still `launched` or `working`; the feed then shows the voyage reaching `voyage.audited`, and `runner`-owned state is visible as `owner: "server"` and actions `["cancel"]` on `GET /api/moons/T1` while it flies.
2. `moon.launch` on a moon that cannot launch (already `audited`) answers 409 with the refusal message, and no voyage is in flight afterwards.
3. `voyage.cancel` of a `slow` voyage answers 200; the voyage parks and the moon's `park_reason` is `interrupted`. Cancelling an unknown voyage id answers 409.
4. Malformed requests: invalid JSON → 400; a JSON array or string body → 400; unknown command → 404; `moon.launch` without `taskId` → 400; `taskId: 5` → 400; `taskId: ""` → 400; an extra field → 400; `config.roles` with `role: "bogus"` → 400; `decision.answer` with `decisionId: "1"` → 400; `Content-Type: text/plain` → 415; a 2 MiB body → 413. After all of them the server still answers `GET /api/ping` with 200, and none of them appended an event.
5. The same `voyage.dock` sent twice answers 200 then 409, and the planet branch has exactly one merge of the moon.
6. The same `decision.answer` sent twice answers 200 then 409.
7. Two `moon.launch` requests for the same moon sent at the same time: exactly one 202 and one 409, and one voyage row.
8. Each synchronous command maps success to 200 with the function's result and a `Refusal` to 409, table-driven over `system.create`, `planet.assign`, `moon.assign`, `moon.reply`, `moon.drop`, `moon.park`, `fleet.retire`, `config.roles`.
9. `moon.assign` with `specPath: "../outside.md"` (and an absolute path outside the repository) answers 400.
10. A run that rejects after it launched is recorded: `createVoyageRunner` tested directly with a hand-written `run` that calls `onLaunched("v1")` and later rejects gives one `Failure` with that task id, voyage id and message, calls `onFailure` once, and `inFlight()` returns to 0. Through HTTP: a failure recorded by the runner appears in `GET /api/snapshot`'s `failures` and a `server` event arrives on the feed.
11. `runner.start` after `abortAll()` rejects with the shutting-down refusal; `abortAll()` with nothing in flight resolves.
12. `srv.close()` with a `slow` voyage in flight parks it as `interrupted`, leaves every ship `idle` or consistently assigned, and resolves; afterwards `rebuild` leaves `dumpProjections` byte-equal (follow how `tests/server/tree.test.mjs` asserts this).
13. A handler that throws an unexpected error answers `500 { error: "internal error" }` with no file path or stack in the body (drive it by making a command function throw a plain `Error` through a stubbed adapter or by testing `errorResponse` directly), and `GET //[x` no longer answers 500.

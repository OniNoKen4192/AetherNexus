## Objective
One end-to-end test proves the release's "done when": a moon is created, launched, rejected by review, replied to, relaunched, approved and merged using only HTTP requests to the server, while a second moon's voyage is in flight the whole time.

## Context
Aether Nexus v0.5 adds a local server and browser page. The page is only a client of the HTTP interface, so a test that drives the whole lifecycle through that interface is the acceptance test of the release; no browser is involved. Everything the test needs already exists (`GET /api/snapshot`, `GET /api/moons/<task-id>`, `GET /api/events`, `POST /api/commands/<name>`). This task adds the test and nothing else: if a step fails because the server misbehaves, that is a defect in an earlier task and must be reported, not patched here. The review outcome cannot be chosen over HTTP (that would be a test hook in the product), so the test steers the fake adapter from inside the test process. Affected workflow IDs is `none` because this project has no review suite.

Steering the review outcome from inside the test process (no product hook): the fake adapter picks its script from `FAKE-SCRIPT: <name>` markers in the job's prompt, and a review prompt without a marker approves. Wrap the galaxy's fake adapter so the first review job for T1 gets `review-reject` and later ones are left alone; `tests/e2e/lifecycle.test.mjs` shows the wrapping pattern (`w.g.adapters.fake = { ...real, dispatch: (job, ctx) => … }`), and `src/server/commands/review.ts` shows the marker being prepended (`FAKE-SCRIPT: ${input.reviewScript}\n${body}`). Read `src/providers/fake/index.ts` to see which field of the job tells a review job from an implement job.

## Constraints
- Every state-changing step goes through `x.api(..., { method: "POST", body })`. The test calls no command function directly. Direct reads of `x.w.g.db` are allowed only in the final assertions (rebuild check, git state), never to decide the next step.
- The world starts from `startWorld("happy", undefined, { server: { pollMs: 20 } })`, which already has one system, one planet and moon `T1` assigned. The test must still exercise creation over HTTP: create a second system, assign a stream to one of its barren planets, and assign two new specs there, `E1` (implement script `happy`) and `E2` (implement script `slow`). The specs are written to disk with `writeSpec` and committed with `x.w.git` before they are assigned, since specs are authored in the editor, not in the page.
- Waiting is always on the feed (`feed.waitFor(predicate, ms)`) with a bounded timeout, never a fixed sleep and never polling the database.
- `x.close()` runs in `finally`, and the feed client is closed before it.
- The test must pass 5 times in a row; it has no timing assumption other than "the `slow` voyage (about 400 ms) is still in flight when E1's first launch is accepted". If that cannot be guaranteed, launch E2 again or restructure so the concurrent-flight assertion is checked where it is true, and say so in the report.
- `node:test` and `node:assert/strict` only; no new dependencies.

## Acceptance

**Test command (must exit 0):**
```bash
npm test -- "tests/e2e/*.test.mjs"
```

**Behavioral criteria** (all in one test titled exactly `REJECT handled entirely over HTTP while a second moon is in flight`, asserted in this order):
1. `GET /api/snapshot` lists `E1` and `E2` in `specs` (with no `error`) after they are committed and before they are assigned; a feed client is opened from that snapshot's `cursor`.
2. `system.create`, `planet.assign` and both `moon.assign` calls answer 200; a new snapshot no longer lists `E1` or `E2` in `specs`, and both moons appear under the new system's planet.
3. `moon.launch` for `E2` answers 202; `moon.launch` for `E1` answers 202 while `GET /api/moons/E2` still shows a voyage with `owner: "server"` (two voyages in flight at once).
4. After the feed shows `voyage.audited` for `E1`, `GET /api/moons/E1` has `actions` deep-equal `["inspect"]`; `voyage.inspect` answers 202.
5. After the feed shows `verdict.issued` for `E1`, the snapshot's `decisions` has exactly one pending decision of kind `reject` whose target is `E1`, and `GET /api/moons/E1` has `actions` deep-equal `["reply","drop"]` and one verdict `REJECT`.
6. `moon.reply { taskId: "E1", note: "it is fine, re-run" }` answers 200, and the actions become `["reply","drop","launch"]`.
7. No pending decision of kind `main_tree_changed` exists for `E2` or `T1` at this point (the reply's own spec write is exempt).
8. `moon.launch` for `E1` answers 202; after `voyage.audited`, `voyage.inspect` answers 202; after the second `verdict.issued`, the actions are deep-equal `["dock"]`.
9. `voyage.dock { taskId: "E1" }` answers 200 with `result.moonStatus === "merged"`; a second identical dock answers 409.
10. The feed shows `voyage.audited` for `E2`, and `GET /api/moons/E2` shows the moon `audited` with actions `["inspect"]`.
11. The ids the feed client received are strictly ascending with none missing from the first snapshot's `cursor + 1` up to the final snapshot's `cursor`.
12. After `x.srv.close()`: `rebuild` leaves `dumpProjections` byte-equal; `git status --porcelain` of the main tree lists only E1's spec file (amended by the reply) as modified; no voyage is in flight.

# Aether Nexus v1 slice 2 — fuel readings, the limiter and refuelling — Implementation Plan

> **For agentic workers:** this plan is lane-tagged for Lanes (`.lanes/config.json`). Run it with `/lanes-run`: DELEGATE tasks are emitted as specs and dispatched; KEEP tasks use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the server knows each provider's remaining fuel where the provider reports it, keeps a reserve, waits out an empty pool by itself, and refuels a freighter on a cheaper Claude model where the owner declared it; the Bridge shows all of it.

**Architecture:** Adapters emit a `fuel` event whenever the provider reports a reading; `runVoyage` stores it as `fuel.reading`. A wall hit stores `fuel.exhausted`. Pure functions in `src/server/limiter/` derive each pool's state from the log and choose the provider for a ship; the scheduler's `plan`, the commands and the snapshot all call them. Nothing is kept in memory.

**Tech Stack:** Node ≥ 22.13, TypeScript, `node:sqlite`, `node:http`; Preact + Vite for the page; tests with `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-15-v1-fuel-design.md` (read it first; section numbers below refer to it).

## Global Constraints

- **Wording (spec §1).** Places don't move, appear or vanish; ships do the moving. A moon is never "out of fuel", "dropped", "launched" or "flying" in comments, messages, page copy or test names. A *ship* is held, runs out of fuel, is refuelled. The work at a moon is its *cargo*; a moon whose freighter ran out of fuel has *cargo awaiting pickup*. Existing identifiers (`moon.launch`, `moon.drop`, `launchMoon`, `dropMoon`, action `"launch"` / `"drop"`) are not renamed.
- **One status, one meaning.** `adrift` means parked and needing a person, nothing else. Out-of-fuel endings use `awaiting_pickup` (moon) and `out_of_fuel` (voyage).
- No new dependencies of any kind.
- Every state change is an appended event with a reducer; after any test scenario `rebuild` must leave `dumpProjections` byte-equal.
- SQL lives only in `src/db/statements.ts` (see `tests/db/registry.test.mjs`).
- Behaviour lives in `src/server/commands/`, `src/server/limiter/` and `src/server/scheduler/`; HTTP handlers and CLI cases are thin wrappers.
- Time is read through `g.now()` (Task 6) in everything this plan adds, never `Date.now()` directly, so tests can move the clock. End-to-end tests that go through `nexus serve` use real time with resets a few hundred milliseconds away.
- No test in the suite calls a real provider. Readings from real providers are checked only in Task 16, with the owner's go.
- Security-routed files (`.lanes/config.json` `routing.security_routed`) are edited only in the KEEP tasks that name them: `src/db/migrations/002.sql` (Task 1) and `src/server/dispatch.ts` (Task 8). Every other task imports from them and does not edit them.
- The scheduler never passes `override`, never answers a decision, never exceeds a concurrency cap.
- Every existing CLI and HTTP command keeps its behaviour except where a task says otherwise.
- Tests import from `dist/`; `npm test` builds first. Run one area with `npm test -- "tests/<dir>/*.test.mjs"`.
- Each task lands as one commit on branch `design/v1-fuel` (a DELEGATE task is committed in its worktree and merged by the Lanes controller, using the task's commit message). End commit messages with `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`.

**Before the run:** set `pipeline.ledger` in `.lanes/config.json` to `.superpowers/sdd/2026-11-15-v1-fuel/progress.md`.

## Review Focus

1. **A provider gives a reset time that is already past, or nonsense.** The pool must not stay dry forever and must not be retried at once: `until` is never earlier than 60 s after the wall hit. Test in Task 7.
2. **A reading that is not a number, is negative, or is above 100%.** It is dropped or clamped to 0..1 at the adapter; the gauge never shows `NaN` and the limiter never divides by it. Tests in Tasks 4, 5 and 6.
3. **The Codex session log is missing, unreadable, or its last line is half-written.** No reading is produced and the voyage ends exactly as it would have. Test in Task 5.
4. **The refuel mapping names a provider with no idle freighter, or one a hand edit removed.** Config load refuses an unknown provider; at run time a missing ship means the moon waits, with no crash and no loop. Tests in Task 6.
5. **Two freighters on the same pool hit the wall at the same moment.** Both moons show cargo awaiting pickup, both are sent a freighter after the reset (within the caps), and neither is parked as a "second hit" because of the other's. Test in Task 13.

// fuel.ts
/** Readings from the newest rate_limits snapshot in the session log of `threadId`; [] when there is none or it cannot be read. Never throws. */
export function readCodexFuel(sessionsRoot: string, threadId: string): AgentEvent[];
export function codexSessionsRoot(env: NodeJS.ProcessEnv): string;   // $CODEX_HOME/sessions, else <home>/.codex/sessions

**Facts (verified on codex-cli 0.145.0):** a session's log is `<root>/YYYY/MM/DD/rollout-<timestamp>-<thread id>.jsonl`, one JSON object per line. Lines carrying a snapshot look like

```json
{"timestamp":"…","type":"event_msg","payload":{"type":"token_count","info":{…},"rate_limits":{"limit_id":"codex","limit_name":null,"primary":{"used_percent":22.0,"window_minutes":10080,"resets_at":1795186480},"secondary":null,"credits":{…},"plan_type":"plus","rate_limit_reached_type":null}}}
```

`primary` and `secondary` have the same shape and either may be `null`; `resets_at` is in seconds. Do not depend on the outer `type` values: take the last line that parses and has an object at `payload.rate_limits`.

**Behaviour:**
- One `fuel` event per non-null window: `window = "<window_minutes>m"`, `used = used_percent / 100` clamped to 0..1 (dropped if not finite), `resets_at` ISO.
- `dispatch` yields `readCodexFuel(...)` once the thread id is known — before the `done` event, and before the error event when the tool result is an error and a thread id can be found. No thread id, no readings.
- When the tool result is an error classified `rate_limited`, the error event carries `resets_at` from the window whose `used` is highest among those just read, if any.
- The fixture file is hand-written from the shape above (three lines: a `session_meta` line, a snapshot, a newer snapshot with both windows); it contains no prompt text.

**Behaviour to test (Review Focus 3):** newest snapshot wins; `secondary` present; root missing; no file for the thread; a file whose last line is cut mid-JSON (the previous snapshot is used); a 5 MB file is read without loading it whole more than once; `used_percent` of `"x"`, `-3`, `250`; `CODEX_HOME` honoured.

**Rules (spec §4.2, §4.3, §4.5):**
- Events read: `fuel.reading` and `fuel.exhausted`, by the `provider` column, payloads `{ window, used, resets_at?, model_family?, source: "reported" }` and `{ until, voyage_id, model_family? }`.
- A model belongs to a family when the family name appears in the model id, case-insensitively. A reading or exhaustion with a family counts only for a model of that family; with no `model` argument everything counts.
- Exhausted = newest matching `fuel.exhausted` has `until` after `g.now()` and no voyage on the provider (of a matching model, when the exhaustion has a family) has `returned_ts` later than that event's `ts`.
- Live reading = `resets_at` after `g.now()`, or no `resets_at` and `ts` within 24 h. Tightest = highest `used`. `remaining = 1 - used`. `reserve_floor` absent = 0.
- `chooseProvider`: `requested` → only that provider (still checked for fuel unless `override`). `override` → the first provider in the role order that is configured, under its caps and has an idle ship, fuel not consulted. Otherwise walk the order; a provider with no adapter, at `per_provider_max`, or with no idle unclaimed ship of the class is skipped silently; one that fails `fuelCheck` is skipped *for fuel*. First that passes → `fly` (with `reroutedFrom` naming the first provider skipped for fuel, if any).

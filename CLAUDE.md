# AetherNexus

Fork of Lanes (https://github.com/OniNoKen4192/Lanes), a Claude Code plugin for cross-model task routing. Substantial changes planned — see "Fork notes" below.

## Communication
- Keep replies concise: lead with the answer or result, then only the detail needed to act on it.
- Teach as you go: when making a non-obvious choice, give the one-sentence "why" (the principle, tradeoff, or mechanism), not a tutorial.
- Separate fact from inference. State what was verified (file read, command run, test output) versus what is assumed, and label guesses as guesses.
- Don't speculate beyond the evidence. If something is unknown, say so and name the check that would resolve it — then run that check when it's cheap.
- Never claim something works without evidence: show the command and its result.

## Workflow
- Read the relevant code before proposing changes; cite locations as `path:line`.
- For multi-file or unclear changes, explore and plan before editing. Small, obvious fixes: just do them.
- Keep diffs scoped to the task. No drive-by refactors; flag them instead.
- Fix root causes, not symptoms. Don't suppress errors or skip hooks/tests to get green.
- Commit only when asked. Work on feature branches, never directly on `main`.
- Every third-party file (3D model, texture, font, sound) gets a line in `assets/LICENSES.md` — source URL and license — in the same commit that adds it.

## Fork notes

- Record divergences from upstream here as they're decided (architecture, renamed modules, dropped features).
- v0 (2026-10-14): `bin/lanes-validate.mjs` and `hooks/` retired; ported to `src/validate`, `src/core/git.ts`, `src/providers/claude-sdk/gate-hook.ts`.
- v0.5 (2026-11-13): `nexus serve` — loopback HTTP server (`src/server/http/`) plus the Bridge page (`web/`, Preact + Vite, built to `dist/web`). The feed is server-sent events, not the WebSocket the parent design first named; commands are HTTP POST. Voyages run concurrently; the single-flight git log is replaced by a per-voyage scope (`withGitLog`). Fuel, limiter and rung selector deferred to v1.
- v1 slice 1 (2026-11-15): the scheduler lives in `src/server/scheduler/` (`plan.ts` decides, `loop.ts` acts) and runs only inside `nexus serve`. `automation.level` now changes behaviour: `manual` does nothing by itself, `verdicts` inspects, docks and re-runs fixes after a human sent the first freighter, `roundabout` also sends the first freighter to every ready moon; `highways` and `autopilot` load as `roundabout` and cannot be selected yet. A first freighter is refused until the moon's dependencies are settled, at every rung. An action refused twice in a row parks the moon (`scheduler_refused` / `scheduler_error`). Design: `docs/superpowers/specs/2026-11-14-v1-scheduler-design.md`.
- v1 slice 2 (2026-11-18): fuel and the limiter (`src/server/limiter/`). Adapters report `fuel` readings, stored as `fuel.reading` (live check 2026-11-19: Codex reports its weekly window as `used_percent` in the session log and in a `token_count` notification; the Claude SDK reports `rate_limit_info.unifiedWindows.<window>.utilization` as a fraction with `resetsAt` in epoch seconds — one sample each, `tests/live/fuel.live.test.mjs`); each provider's pool is `ok`, `low` (below `pool.reserve_floor`), `dry` (a ship hit the wall, until the reset), `unknown` or `free`. Every launch and inspection asks the limiter first, whoever sends it: a low pool holds freighters, a dry pool holds customs too, a held ship is rerouted down the role order or waits (`limiter.held`, never a park). A ship that hits the wall mid-run ends `out_of_fuel`, is released, and the moon's cargo is `awaiting_pickup` (customs: back to `audited`); the scheduler sends the next ship after the reset. A second hit in a row on the same provider parks the moon `rate_limited`. `adrift` now means only "needs a person". `pool.refuel { provider, models, min_wait_minutes }` lets a held freighter fly a cheaper model on another provider instead of waiting (`limiter.refuelled`, `refuel_for`). A pickup whose cargo fails its audit parks with the Bridge wording "contraband in the cargo" (`carryover_violations`) or "raided by pirates" (`baseline_tampered`). Bridge: fuel gauge per provider, "waiting on <provider> fuel", `Refuel`, `Send anyway`; CLI `--override`, `--refuel`. Migration 002 adds the two statuses. Design: `docs/superpowers/specs/2026-11-15-v1-fuel-design.md`; plan: `docs/superpowers/plans/2026-11-15-v1-fuel.md`.
- Command names (2026-11-19): commands are named after what moves, never "verb the moon". `delivery.send` / `sendDelivery` / `nexus delivery send` (was `moon.launch`), `customs.send` / `sendCustoms` (was `voyage.inspect`), `cargo.dock` / `dockCargo` (was `voyage.dock`), `delivery.cancel` / `cancelDelivery` (was `moon.drop`); no aliases. Action names: `send`, `inspect`, `dock`, `cancel_delivery`. Files: `src/server/commands/delivery.ts`, `customs.ts`. The job is a "delivery"; "freighter" is to become one ship tier, so new command and function names must not use it for the job.
- Ship catalogue (2026-11-19): a ship is a lasting record — `job` (`delivery`, `customs`, `transfer`, `survey`; was `class`), `fleet` (the provider), `faction`, `weight`, and a full copy of its `formation` — and is commissioned on demand inside the launch transaction (`ship.commissioned` then `voyage.launched`, appended together by `appendAll`) when no idle ship of the same fleet, job and weight exists. `nexus init` registers no fleet; fleet size is never a limit and nothing says "all … are assigned" any more: the only limits are `scheduler.max_concurrent_ships`, `scheduler.per_provider_max`, dependencies and fuel (no cap on open deliveries — the owner's decision). The weight of a trip comes from `providers.<id>.weights` (first hit: the model id the voyage is told to fly, then the moon's tier for a delivery with no model, then `default`, then `standard`); the faction from `providers.<id>.faction` (default: the provider id; `codex` → `openai`, `claude` → `anthropic`). Formations, cargo kinds, weights and per-faction name rules live in the catalogue: built-in data in `src/core/catalogue/`, extended by an optional `.nexus/catalogue.json` (formations and cargo merge by `id`; a `weights` list and a faction's name rules replace whole). A delivery's cargo is drawn per trip and stored on the voyage. Picks are seeded from `fleet.seed` and the ship or voyage count; reducers copy everything from the event and never read the catalogue or the config. Migration 003 maps old ships (`freighter` → `delivery`, `customs` → `customs`, `carrier` → `transfer`, `surveyor` → `survey`; faction = fleet, weight `standard`, formation `legacy-<job>`), and the `ship.registered` reducer writes the same rows. Reads: `snapshot.fleet` (formation parsed), voyage `cargo` and `ship`, `snapshot.weights`; `nexus fleet` prints name, fleet, faction, job, weight, formation, status, voyages; the Bridge shows them in words (`web/src/ships.ts`), no images yet. Wording: "freighter" and "carrier" are hulls and formation names in catalogue data and nothing else (`tests/wording.test.mjs` enforces it for `src/`, `web/src/` and `prompts/`). Design: `docs/superpowers/specs/2026-11-19-ship-catalogue-design.md`; plan: `docs/superpowers/plans/2026-11-19-ship-catalogue.md`.
- Still open: the stored words `dropped` (moon status, `moon.dropped`) and the `drop` outcome are in the log and need a migration; the legacy class `freighter` survives only in old `ship.registered` events; ship art per faction is not designed yet.

## Commands
- `npm install` (SDK + MCP client deps; Preact + Vite as dev deps); `npm run build` (tsc to `dist/`, then `npm run build:web` builds the Bridge page from `web/` to `dist/web`).
- `npm test`: full suite, about 4 minutes, builds first. One area: `npm test -- "tests/<dir>/*.test.mjs"` (Node 22.14 rejects a bare directory argument).
- Real adapters: `NEXUS_LIVE=1 npm test -- "tests/live/*.test.mjs"`. Never CI; spends the user's pool, so ask first.
- Validator selftest: `node dist/cli/main.js validate --selftest`
- Bridge: `node dist/cli/main.js serve [--port <n>]` (127.0.0.1, default 7341; open the printed URL). Also `nexus events --follow` and `nexus decision answer <id> --mine | --not-mine`.
- Trust rung: `nexus config set trust <manual|verdicts|roundabout>` (a running server picks the change up), or the selector in the Bridge header.
- CI (`.github/workflows/ci.yml`) runs the suite on Linux, Windows and macOS.

## Gotchas
- `npm test` builds first; a stale `dist/` is the usual cause of a test importing a function that "does not exist".
- `node:sqlite` prints an ExperimentalWarning unless run via the npm scripts or the `nexus` entry.
- `npm install` / `npm audit fix` on Windows can drop the optional `@emnapi/core` and `@emnapi/runtime` lock entries, and `npm ci` then fails on Linux and macOS CI: check `git diff package-lock.json` before pushing.
- The default `roles.implement` is `["codex", "fake"]` and `roles.review` is `["claude", "fake"]`. A reroute walks that order, so a galaxy that keeps the default sends a held delivery to the `fake` provider, which does no real work: set the roles before running unattended.
- Tests: `makeGalaxy` (tests/helpers.mjs) makes every non-fake adapter throw, so a test cannot spend a real pool. A config patch must still pin `c.roles` to fake providers, or its voyages park `backend_failure` with that guard's message. The guard does not cover a second `openGalaxy` handle or a CLI child process.
- The limiter's clock is `g.now()`; a wall hit holds a pool for at least 60 s whatever reset the provider gave. Tests move `g.now` instead of sleeping.
- `fleet.freighters`, `fleet.customs`, `fleet.carriers` and `fleet.surveyors` are still accepted in `.nexus/config.json` and ignored: ships are commissioned on demand. `fleet.name_theme` and `fleet.seed` still matter.
- `.nexus/catalogue.json` and `providers.<id>.weights` are read when a galaxy is opened; an invalid catalogue, or a weight the catalogue does not list, refuses the open (and a running server refuses to reload such a config). A catalogue edit needs a restart of `nexus serve`, and never changes a ship that already exists.
- An event that ends a voyage is written in one transaction with the release of its ship (`appendAll`): customs' return, a supersede (FIX, reply, cancel), out of fuel, a dock. Keep it that way when adding a new way for a voyage to end. A ship stranded by an older build (`assigned`, no open or parked voyage) is released when `nexus serve` starts and by `nexus fleet recover`, logged as `ship.released` with outcome `recovered`. Plain `nexus fleet` only reads.
- Customs' verdict and what it does to the delivery are one transaction (`recordVerdict` in `src/server/commands/customs.ts`), but the customs voyage's return is written before it. A crash in between leaves the moon `reviewing` with the verdict only in the voyage's report: `inspect` is then offered, and `sendCustoms` records the stored verdict without flying a ship or asking the limiter (`unrecordedReturn`). So `inspect` on a `reviewing` moon never launches anything.
- Tests: a new galaxy has no ships. To get an idle ship without a launch use `idleShip(db, fleet, job, weight)` from `tests/fixtures/world.mjs`; `seedFleet` registers ships the old way (legacy rows).
- A Lanes worktree has no `node_modules`; `tests/http/page-*.test.mjs` run `tsc` from `process.cwd()/node_modules`, so link the main tree's `node_modules` into the worktree (a junction) before the full suite, and remove the link before `worktree remove`.
- The upstream Lanes plugin (`lanes@lanes`) is installed in this Claude Code environment; editing files here does not change it.
